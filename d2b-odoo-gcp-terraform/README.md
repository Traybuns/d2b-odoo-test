# Data2Bots Odoo — GCP Terraform

This Terraform deploys the dev Odoo environment described by the
`Traybuns/d2b-odoo-test` repository.

## Architecture

Global HTTPS Load Balancer
→ Compute Engine VM
→ Docker Compose / Traefik / Odoo / Cloud SQL Auth Proxy
→ Cloud SQL PostgreSQL

Cloud DNS provides:

`internal.odoo.data2bots.com` → the global load-balancer IP.

Secrets are generated by Terraform and stored in Secret Manager. The VM
runtime service account retrieves them at boot; no service-account key file
is created.

## Prerequisites

1. A GCP project named `d2b-odoo-dev`.
2. Billing enabled.
3. An existing Cloud DNS managed zone for `data2bots.com`.
4. Terraform >= 1.6.
5. `gcloud` authenticated with permission to create project resources.

## Deploy

Copy the example variables:

```bash
cp terraform.tfvars.example terraform.tfvars
```

Set `dns_zone_name` to the exact existing Cloud DNS managed-zone name.

Then:

```bash
gcloud auth application-default login
gcloud config set project d2b-odoo-dev

terraform init
terraform fmt -recursive
terraform validate
terraform plan
terraform apply
```

After apply, wait for the Google-managed certificate to become ACTIVE and
for the VM startup script to finish.

Check:

```bash
terraform output
gcloud compute instances get-serial-port-output d2b-vm-odoo-dev-01 --zone=europe-west4-b
gcloud compute ssh d2b-vm-odoo-dev-01 --zone=europe-west4-b --tunnel-through-iap
```

## Multi-client model

The initial deployment creates:

- `d2b_odoo_internal`
- `internal.odoo.data2bots.com`

The Odoo configuration already uses:

`db_filter = ^d2b_odoo_%d$`

For a future client, the infrastructure can be extended with a database,
DNS record, hostname rule, and certificate hostname. The current repository's
Traefik rules are explicitly single-host, so client onboarding should update
the application repository as well.

## Important repository compatibility note

The repository's current `docker-compose.yml` starts Cloud SQL Auth Proxy
without `--private-ip`. The Terraform intentionally creates Cloud SQL with
private IP only for a hardened network posture, so **before production use**
update the proxy command in `docker-compose.yml` to include:

`--private-ip`

Once that repository change is made, the proxy will use Cloud SQL's private
address from the VM VPC.

If you prefer zero repository changes for this first dev deployment, change
the Cloud SQL `ipv4_enabled` setting to true and remove the private-only
assumption, but that is less hardened.
